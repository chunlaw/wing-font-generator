# Hybrid annotation design — baked composites + composable marks

Status: **implemented** (phases 1–6 below); cross-engine render matrix
(phase 7) still open. Scope: **CJK / full-width bases**; DIY annotation
inventory **bounded by an optional user-supplied CSV `A`**
(`--diy-annotations`).

## Goal

Keep the pipeline exactly as-is for the *automatic, context-correct* path
(baked base+annotation composites selected by `ccmp` chain-context /
ligature / IVS), and add a *parallel manual path* that lets a reader attach
**any annotation string listed in CSV `A`** to **any** base character —
including `(base, annotation)` pairs that never appear in the mapping CSV.

`A` is the curated, bounded inventory — the font author controls exactly
which annotations exist. Ready-made inventories live in
`python/diy-mappings/<language>/*.diy-annotation.csv` (generated by e.g.
`diy-mappings/cantonese/gen_canto_diy.py`) and are what the CI builds use.

The manual path treats each A-entry as a **zero-advance mark glyph** whose
position is baked into its own outline, and the reader swaps the base under
it to a bare, annotation-free glyph so the two layers do not collide.

### Why not composite each `(base, A-string)` pair

Baking one composite per `(base, string)` is multiplicative: glyph count
**and** ligature-rule count become `#bases × |A|`. Against the full CJK range
(~20k+ chars) even `|A| = 4` exceeds the **65,535 `numGlyphs` hard cap**,
and component-based composites shrink bytes but not the slot count.
Rendering each A-string **once** as a shared mark makes both counts additive
(`|A| + bases`). Trade-off: per-pair composites would be as robust as the
automatic output, but cannot cover an unbounded base set under the cap.

Nothing about the existing baked-composite output changes; this is additive.

## 1. Three glyph kinds in the output

| Kind | Name | Source |
|------|------|--------|
| **Baked composite** (base + default/variant annotation) | cmap glyph / `wingfontNNNNNN` | `generate_annotated_glyphs` |
| **Bare scaled-base** (base at `base_scale`, *no* annotation) | `wingfontbare…` | `generate_annotated_glyphs(emit_bare_bases=True)` |
| **DIY mark** (annotation only, zero advance) | `wingfontmark<ID-HEX>` | `generate_mark_glyphs` |

Bare bases are needed because variant 0 of a mapped character reuses the
codepoint's own glyph name with the default reading baked in, so a mark
stacked on it would double up. Bare bases are **not DIY-only**: every build
emits them (they are also the target of `字0` and IVS `VS256`), unless the
pre-flight glyph budget (`cli._check_glyph_count_budget`) predicts an overflow, in which case they are skipped with a
note and `字0` renders a literal `0`. Un-mapped characters already render
bare via `scale_glyphs`.

## 2. The DIY inventory — CSV `A`

`diy_handler.build_diy_inventory`. Format: two columns, **`input,annotation`**:

```
ｚａａ１,zaa1        # type full-width ｚａａ１ → render "zaa1"
coeng1,coeng˥      # type ASCII coeng1   → render a diacritic form
zaa1,ザー           # type romanization   → render Katakana
zaa1               # 1-col shorthand ≡ ｚａａ１,zaa1 (input auto-derived)
,ザー               # empty input → no typed route (cmap route only, §4c)
```

* **annotation** (2nd field) is what renders: shaped by the annotation font
  into the mark glyph. It can be ANY string — Latin, diacritics, Katakana,
  Hangul, Thai — because the reader never types it directly.
* **input** (1st field) is the literal sequence the reader types; its
  glyphs (from the BASE font) ligate into the mark (§4a). Full-width forms
  (U+FF01–FF5E) are recommended (see §5 on runs).
* One column is shorthand: input = full-width form of the annotation
  (skipped, with a log line, if the annotation isn't printable ASCII).
* Several rows may share one annotation (many inputs → one mark); a
  duplicate input keeps its first row. `#` lines and blank lines are
  skipped; fields over 32 chars are dropped.

**Mark ids.** Each distinct annotation gets a Plane-15 number
(`U+F0000` upward) used **only** as an internal id: it names the glyph
(`wingfontmarkF0000`) and fixes its slot in the cmap route (§4c). It is
never itself put in cmap. Ids follow **CSV row order (first appearance)**,
not an alphabetical sort — the slot is baked into documents the PowerPoint
add-in has converted, so **appending** to `A` must not renumber existing
annotations. Reordering or deleting rows does renumber them; treat a
shipped inventory as append-only.

## 3. Build-pipeline changes

### 3a. Mark glyphs — `build_glyph.generate_mark_glyphs`

For each `(annotation, id)`:

- Shape with the same HarfBuzz helpers the composite path uses
  (`_shape_run`, `_shaped_width`, `_draw_shaped`) and the **same
  `anno_scale_eff`**, so a DIY annotation is visually identical to a baked
  one. Annotations that shape to nothing are skipped with a log line.
- Draw **only** the annotation. A mark is a *trailing* zero-advance glyph,
  so the shaper draws it one base advance to the right of the base cell;
  to land over the base the outline is shifted back:
  `x_start = -(assumed_base_advance + anno_len) / 2 + mark_x_offset·em`
  (`assumed_base_advance` defaults to the output em). Vertical position
  follows the build's mode: `anno_y_offset = round(em × upper_y_offset_ratio)`
  normally, below the baseline under `--anno-below`, `0` under `-v`.
- `hmtx[mark] = (0, lsb)` with **`lsb = round(xMin)`** of the ink (see §5,
  load-bearing); `vmtx` gets `(em, 0)` when present.
- Ink `max_y` / `min_y` feed `char_metrics`, so the existing auto-fit
  ascent (`--out-ascent auto`) covers tall marks with no new code.
- Add the cmap route entry (§4c).

No GPOS anchors: position is baked into the outline, the same robustness
trade Wing makes for composites (and avoids CJK GPOS suppression).

### 3b. Bare bases

See §1. `generate_annotated_glyphs` fills
`bare_base_map = {default_base_glyph: bare_glyph}`; advance = the base's
real advance.

## 4. Reaching a mark

> **Script-run itemization.** Browsers split text into runs by Unicode
> *script* before shaping, and GSUB can't act across a run boundary. Han
> `行` and full-width Latin `ｚａａ１` land in different runs, so no lookup
> can see both. The pieces below are therefore decoupled, each working
> **within its own run**.

### 4a. Typed input → mark (route B) — `mark_input_handler.buildMarkInputLiga`

GSUB Type 4 under `ccmp`, one ligature per input:

```
(ｚ, ａ, ａ, １) -> wingfontmark…(zaa1)
```

Input characters resolve to BASE-font glyphs; an input with any character
missing from the base font is skipped. fontTools orders ligatures
longest-first, so a longer input beats a shared prefix. There is no
trigger: any run that exactly spells an inventory input ligates, even
with no base before it (a harmless floating annotation).

### 4b. Stripping the base — `０` / `0` (liga_handler)

The reader types the full-width digit zero after the base:
`行０ｚａａ１`. `０` is script **Common**, so it stays in the Han run, and
`liga_handler.buildLiga` (given `bare_base_map`) emits

```
(行, ０) -> bare行      (also (行, 0) for ASCII)
```

as part of the standard 1-indexed digit semantics (`字0` = bare, `字1` =
default, `字N` = N-th reading). This is **not** a DIY-specific lookup: it
exists in every build with bare bases. Without the `０`, a mapped base keeps
its baked reading and the mark stacks on top of it.

Net result in browsers and single-run apps alike: `[bare行, zaa1 mark]`.

`mark_strip_handler.buildBareStripLiga` (a standalone `(base, ０)` ligature)
and `buildBaseStrip` (the original chain-context "strip when a mark follows"
rule, which can't work across script runs) remain in the module but the
pipeline no longer calls either.

### 4c. cmap route for apps without GSUB (route A)

Windows PowerPoint doesn't run GSUB on these fonts, so the
[PowerPoint add-in](https://github.com/chunlaw/wing-font-ppt-addin) shapes
the text with HarfBuzz and rewrites it to a sequence that reaches the same
glyphs through cmap alone. For marks that sequence is a **BMP PUA carrier
plus an optional variation selector** (`diy_handler.mark_sequence`):

- mark index `i` (= id − U+F0000) → carrier `U+E000 + i // 241`;
- slot `i % 241 == 0` → the carrier alone (format-4/12 entry);
- otherwise → `carrier + VS(16 + slot)`, i.e. VS17…VS256 (format-14 entry).

Why not Plane-15 directly: PowerPoint renders Plane-15 PUA with a fallback
font regardless of the run font (tested Oct 2026, Office 16.0 build 20326)
but honours BMP PUA and variation sequences. BMP PUA has only 6,400 slots —
fewer than the LSHK (7,200) or Taiwanese (10,458) inventories — hence 241
marks per carrier. Bare bases are reached the same way via `base + VS256`.

### 4d. GDEF

`mark_strip_handler.tagMarksAsGdefMarks` sets GDEF class 3 (mark) on every
mark glyph — **only if** the font already has a `GlyphClassDef`.
Fabricating one would reclassify every other glyph (same rule as
`word_liga_handler`); without it, marks rely on their zero advance.

### 4e. Lookup order and timing

All DIY GSUB is built **before the subset**, in the main GSUB phase:

1. `buildMarkInputLiga` (lowest lookup index) + GDEF tagging;
2. chain-context pass 1 (compound variant overrides);
3. `buildLiga` — digit / `丅` overrides including `(base, ０) → bare`;
4. chain-context pass 2 (default compound rules).

Everything here is plain ligatures, so there is no probe-compile overflow
on the ~80k-glyph pre-subset font. (An earlier chain-context strip had to
be built post-subset because its mark coverage held glyph IDs > 65,535;
that rule is gone.)

## 5. Constraints & risks

- **DIY requires `-opt`.** A full CJK base is ~50k glyphs on its own
  (ChironSungHK-R: 50,351), so an un-subsetted build of any large mapping
  overflows 65,535 before DIY adds a mark. The subset keep-list adds the
  marks, bare bases and the full-width input codepoints; the carriers and
  selectors survive with the kept mark glyphs (verified on CI's
  `WingSansYueThai.ttf`: 18 carriers + 4,206 carrier UVS entries). A
  character the mapping never reaches is dropped by the subset and can't be
  DIY-annotated — the one accepted limitation.
- **CJK / full-width bases only.** A mark is one glyph shared by every
  base, so it assumes the base advance (= em). Exact for CJK ideographs;
  for variable-width bases it lands off-centre by
  ~`(real_advance − assumed)/2`. Non-CJK base scripts use the word-unit
  composite path instead.
- **Inventory must be append-only** once documents exist (§2).

### Cross-run positioning (Word vs browser) and the `lsb` invariant

Browsers itemise `行０ｚａａ１` into a Han run `[行０]→bare` and a Latin run
`[ｚａａ１]→mark`, so the mark is an **orphaned zero-advance glyph in its own
run**. DirectWrite/Word keep the whole EAW=Fullwidth sequence in one run.
Both consequences were verified with diagnostic fonts (`DIAG*` sweeps):

1. **`lsb` MUST equal the outline `xMin`.** These renderers position the
   orphaned mark relative to its `hmtx` left-side-bearing (phantom-point
   semantics). A stale `lsb` makes the renderer shift the glyph back,
   cancelling the move. `generate_mark_glyphs` sets `lsb = round(min(xs))`
   and `test_mark_glyphs` asserts it (including with non-zero
   `mark_x_offset`). Do not "optimise" it to 0.

2. **Different pen origins.** With `lsb` correct, Word draws the mark
   centred over the base. Browsers start the Latin run ~`0.125·em` to the
   **right** of the font's assumption (length-independent, roughly constant
   for full-width bases), so the same mark looks shifted right there. The
   font geometry is centred (measured: mark ink centre 501 vs bare-base ink
   centre 492); the residual is the browser's origin, which the font can't
   observe. `--mark-x-offset` (fraction of em) exposes the trade:

   - `0.0` (**default**) — geometric centre, correct in **Word/print**;
     browsers show it ~`0.125·em` right.
   - `-0.0625` — splits the difference (~`0.06·em` off in each).
   - `-0.125` — favours the **browser**; Word shows it ~`0.125·em` left.

   Dead-centre everywhere needs the composite path (base+annotation in one
   glyph) at `#bases × |A|` glyphs — the explosion this design avoids.

   for Cantonese (all schemes and cross-script variants), Mandarin and
